EVENTRA
Frontend V2 — Product Architecture & UX Specification
Autonomous Event Operations: Discovery → Engagement → Execution → Recovery
Implementation starting point • 27 September 2026
1. Executive Summary
EVENTRA’s current frontend is visually polished but its information architecture does not communicate the actual product. It currently reads primarily as a live-event command/control dashboard. The product vision is broader: EVENTRA should understand an event, discover real venues and vendors, qualify and rank them against event requirements, contact shortlisted providers, understand provider responses, execute authorized actions, detect operational deviations, and recover from them.
Frontend V2 must therefore be designed around one continuous operational loop rather than a collection of disconnected pages.
EVENT SPECIFICATION      ↓AGENT DISCOVERY      ↓QUALIFICATION + DEDUPLICATION      ↓DETERMINISTIC CONSTRAINT CHECK      ↓SHORTLIST      ↓ENGAGEMENT: CALL / WHATSAPP / EMAIL      ↓RESPONSES + QUOTE EXTRACTION      ↓AGENT ANALYSIS      ↓DETERMINISTIC VALIDATION      ↓APPROVAL / AUTHORIZED EXECUTION      ↓LIVE EVENT OPERATIONS      ↓INCOMING SIGNALS / INCIDENTS      ↓IMPACT ENGINE + RECOVERY AGENT      ↓RECOVERY + VERIFICATION
2. Core Product Principle
The frontend must make the separation between the agentic AI layer and deterministic engine explicit. The user should be able to tell what the agent proposed, what the deterministic system verified, what came from an external source, and what action was actually executed.

Non-negotiable UX rule: the frontend must not invent business facts, availability, capacity, pricing, provider responses or execution status. It renders authoritative backend state and clearly labels unknown or unverified information.
3. Frontend V2 Goals
Make EVENTRA’s event lifecycle immediately understandable.
Make agentic discovery visible and inspectable rather than hiding it behind a loading spinner.
Show real map-based venue/vendor discovery with candidate counts and geographic context.
Show the transformation from raw discoveries to qualified, matching and shortlisted candidates.
Make calling, WhatsApp, email, quote collection and negotiation visible as actual execution workflows.
Surface incoming provider messages in UX and allow those messages to trigger structured agent workflows.
Connect provider communication directly to incidents, deterministic impact analysis and recovery.
Expose provenance and evidence for important recommendations.
Keep the existing deterministic backend engines authoritative.
Keep the landing page and strong existing visual identity where appropriate.
4. Explicit Non-Goals
Do not rebuild the backend architecture merely to support the frontend redesign.
Do not move deterministic calculations into React/frontend code.
Do not turn EVENTRA into a generic chatbot.
Do not fabricate provider facts when a source does not provide them.
Do not make the live command-center experience the entire identity of EVENTRA; it is the execution phase of a larger lifecycle.
Do not hide autonomous actions. Every consequential action should have a visible execution state and audit trail.

6. Overview / Event Home
The Overview becomes the real home for an event. It should answer: What is this event? What stage is it in? What is complete? What needs attention? What is EVENTRA doing right now?
Event identity: name, event type, dates, location, guest count.
Operational readiness percentage derived from backend state.
Lifecycle progress: Specification → Discovery → Planning → Readiness → Live.
Agent activity panel showing current or recent autonomous work.
Deterministic health panel showing feasibility/status of budget, schedule, capacity and critical dependencies.
Open decisions / approvals.
Active incidents or unresolved risks.
Recent discovery and engagement results.

Discovery is a hero workflow and should not be buried under a simple Venue or Providers CRUD page. It is the visual proof that EVENTRA can search the real world, reason over results and produce event-specific matches.

8.2 Dynamic Discovery Funnel
The UI must never hardcode the numbers. Backend returns a discovery run and the frontend renders the actual counts:
{  "run_id": "disc_123",  "event_id": "...",  "category": "venue",  "discovered": 100,  "unique": 31,  "relevant": 18,  "matching": 13,  "shortlisted": 5,  "iterations": 2,  "status": "target_reached"}
The numbers should be dynamic. One run may be 47 → 31 → 18 → 13 → 5; another may be 100 → 67 → 29 → 13 → 5.

9. Qualification, Matching & Ranking UX
The UI must distinguish qualification from ranking. A high rating does not make a provider relevant. A candidate must first be the requested provider type, plausibly serve the event, and satisfy commercial/contactability rules where applicable.
DISCOVERED   ↓QUALIFIED?   ↓ YESHARD CONSTRAINTS PASS?   ↓ YESRANK   ↓SHORTLIST
Example ranking dimensions can include event fit, location, rating, review volume, contactability, data completeness and business legitimacy. Scores must be calculated from actual evidence, not invented by the LLM.
Every recommendation should expose component reasoning rather than only a mysterious overall score.
10. Venue Discovery
Inputs: location, guest count, event type, date, radius, budget, required amenities and other hard requirements.
Map-first discovery experience.
Show discovered → unique → relevant → matching → shortlisted counts.
Hard requirements such as capacity must be checked before ranking.
Unknown data must remain unknown; never infer a factual capacity or price without evidence.
Show venue suitability score with evidence.
Allow shortlist, compare and proceed to engagement where contactable.
11. Vendor Discovery
Reuse the same discovery framework as venues.
Provider category is explicit: catering, AV, photography, decoration, security, transport, etc.
Show event fit and commercial relevance.
Map displays actual provider locations.
Show discovered → unique → relevant → matching → shortlisted funnel.
Provider-specific constraints can affect qualification and ranking.
Shortlisted vendors transition directly into Engagement.

14. Agent Interpretation of Incoming Messages
Incoming provider messages can be operational signals. The system should display the original message, then the structured interpretation produced by the agent.
VENDOR MESSAGE"Sir, I'm stuck in traffic and I won't be able to come."✦ AGENT INTERPRETATIONIntent: PROVIDER_UNAVAILABLEConfidence: 96%Affected service: CATERINGSeverity: CRITICALRequires recovery: YES
The original message remains visible and auditable. The interpretation is a separate layer and should never overwrite the source message.

24. Autonomy & Authorization UX
The frontend should make authorization policy visible. The agent can propose and orchestrate, but consequential actions must respect the configured autonomy policy.
AGENT PROPOSES      ↓POLICY CHECK      ↓┌──────────────────────────────┐│ AUTO EXECUTE                 ││ or                           ││ APPROVAL REQUIRED            │└──────────────────────────────┘      ↓TOOL EXECUTION      ↓VERIFICATION
Example: a recovery action below a configured budget threshold may be auto-executable; a higher-cost replacement may require organizer approval. The frontend should show the reason an approval is or is not required.
25. Visual Design Direction
Keep the strong dark visual identity, but move away from a purely sci-fi/military control-room aesthetic. The target is premium operational software with an AI-native layer.
Keep dark foundation and strong contrast.
Keep EVENTRA accent color for active/autonomous states.
Reduce excessive glow, glass and decorative cards.
Use clear information hierarchy and generous spacing.
Use color semantically: agent, engine verified, warning, critical, success, unknown.
Prefer evidence-rich panels over decorative dashboards.
Maps should be real and functional.
Animations should communicate state transitions, not exist only for visual effect.
Use compact operational typography for metadata and larger typography for decisions/outcomes.
Make the system feel trustworthy and explainable.

28. Frontend V2 Acceptance Criteria
A new user can understand EVENTRA’s purpose within the first screen.
The event lifecycle is visible without opening multiple menus.
Venue discovery displays a real map and actual discovery counts.
Vendor discovery displays a real map and actual discovery counts.
The UI can show a funnel such as 100 discovered → 31 unique → 18 relevant → 13 matching → 5 shortlisted.
Discovery iterations and adaptive search decisions are visible.
A candidate can be opened to inspect evidence and why it matched.
Agent proposals are visually distinct from deterministic engine results.
Shortlisted providers can transition directly into outreach.
Call and WhatsApp execution states are visible.
Incoming provider WhatsApp messages are visible in the UX.
A provider cancellation can become an incident through the backend workflow.
The deterministic impact engine can show affected tasks, schedule and budget impact.
Recovery discovery and backup-provider outreach are visible.
Provider responses can be displayed with structured extracted facts.
Deterministic validation can be shown after agent extraction.
Approval state is visible before consequential actions.
Every autonomous action has a visible execution/audit trail.
Unknown/unverified facts remain explicitly unknown.
No frontend business logic duplicates authoritative deterministic backend calculations.

31. North-Star UX Statement
EVENTRA should feel like one continuous autonomous event-operation loop: Find → qualify → shortlist → contact → converse → extract → evaluate → recommend → approve → execute → monitor → recover.
The frontend is successful when a user can watch that loop happen with real evidence, while always understanding the boundary between what the agent proposed, what the deterministic engine verified, what the external world reported, and what EVENTRA actually executed.
